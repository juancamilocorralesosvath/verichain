# H5.2 — Registro, aprobación y rotación de llaves públicas

## Contexto

Diseño §7b "Ciclo de vida de las llaves". Las llaves viejas nunca se borran, para que los bloques antiguos sigan verificando.

## Especificación

- Modelo `LlaveUsuario { id, usuario_id, version, spki_b64, estado ('pendiente'|'aprobada'|'reemplazada'|'rechazada'), creado_en, aprobada_por?, aprobada_en? }`.
- `POST /api/llaves { spki_b64 }` (registrador):
  - Valida que sea una llave pública EC P-256 SPKI. Usa `crypto.createPublicKey` y revisa `asymmetricKeyDetails.namedCurve === 'prime256v1'`.
  - Queda `pendiente`, con `version` = la última versión del usuario + 1.
- `GET /api/llaves/mias` (registrador). `GET /api/llaves/pendientes` (admin).
- `POST /api/llaves/:id/aprobar` y `/rechazar` (admin). Al aprobar, la llave `aprobada` anterior del mismo usuario pasa a `reemplazada`. Solo puede haber **una** aprobada por usuario.
- Para la verificación, `llavesUsuarios` incluye las llaves `aprobada` y `reemplazada`.
- Los eventos de registro, aprobación y rechazo dejan un `TODO(H7.2)` para la bitácora.

## Criterios de aceptación

- [x] e2e: registrar → pendiente; el admin aprueba → aprobada. Registrar otra y aprobarla → la primera pasa a `reemplazada` y la nueva tiene `version 2`.
- [x] e2e: una llave RSA o un base64 basura → 400.
- [x] e2e: un registrador no puede aprobar llaves (403) y el admin no puede registrar una para sí mismo (403, según la matriz).

## Notas de traspaso

### Decisiones tomadas

- **Una aprobada por usuario también en la BD:** índice único parcial `WHERE estado = 'aprobada'` añadido a mano en la migración `llaves`. Prisma no lo marca como desvío (`migrate dev` no generó migraciones nuevas), y el servicio además retira primero la vigente dentro de la transacción.
- **Llave única globalmente** (`spki_b64 @unique`): una misma llave no puede registrarse dos veces, ni por otro usuario (409 `Registro duplicado`); si no, el no repudio no identificaría a un solo firmante. La historia no lo exigía.
- **Validación:** DTO (base64, máx. 200) y, en el servicio, base64 canónico + `createPublicKey` + `ec`/`prime256v1`. RSA, P-384 y basura dan 400 `Llave pública inválida`.
- **Estados:** aprobar y rechazar solo parten de `pendiente` (si no, 409); id inexistente 404; id no numérico 400. Aprobar/rechazar responden 200. Los registros y aprobaciones van por la misma `Cola` que los anexos.
- `creado_en` y `aprobada_en` son `DateTime` (como `Usuario`). Las respuestas usan un mapeo explícito (sin `usuario_id` ni `aprobada_por`); `/pendientes` añade `username`.
- `LlavesService.llavesParaVerificacion()` (aprobadas y reemplazadas) ya se pasa como `llavesUsuarios` a `verificarCadena`; todavía no tiene efecto porque aún no se inyecta `verificarFirma` (H5.3/H5.4).
- Auditor: 403 en todos los endpoints de llaves. Eventos con `TODO(H7.2)`.
- No se tocó `roles.e2e.test.ts`: su prueba genérica ya exige 401 sin sesión en las rutas nuevas; la matriz por rol de llaves está en `llaves.e2e.test.ts`.
