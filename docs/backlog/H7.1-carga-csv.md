# H7.1 — Carga masiva desde CSV con firma por lotes

## Contexto

Diseño §5.6. El enunciado dice "a partir de una tabla de datos": esto permite cargar la tabla inicial.

## Especificación

- `POST /api/bloques/preparar-lote` (registrador), multipart con el campo `archivo`:
  - Máximo 200 KB y 500 filas.
  - Solo `text/csv` o `.csv`.
  - Encabezado exacto `cedula,nombre,direccion,telefono`.
  - Usa una librería de parsing probada (p. ej. `csv-parse`), nunca `split(',')`.
- Valida cada fila con las **mismas** reglas de `CrearPersonaDto` (reutiliza el validador, no lo copies), además de cédulas duplicadas dentro del archivo y contra la BD.
- Respuesta: `{ validas: [{ fila, borrador_id, hash_datos }], invalidas: [{ fila, errores: string[] }] }`. Solo las válidas generan borrador.
- `POST /api/bloques/confirmar-lote { items: [{ borrador_id, llave_id, firma_b64 }] }`: confirma en el orden recibido aplicando las mismas reglas de H5.3. Si una falla, se detiene y reporta cuáles quedaron anexadas.
- Web: en la página Personas, subir el CSV → mostrar válidas e inválidas → "Firmar y anexar N" firma todas con la llave local → confirmar.
- Incluye `docs/ejemplos/personas.csv` con unas 10 filas ficticias, más 2 inválidas para la demo.

## Criterios de aceptación

- [x] e2e: CSV con 8 filas válidas y 2 inválidas → 8 borradores; confirmar el lote → 8 bloques nuevos y la cadena es válida.
- [x] e2e: un archivo de 300 KB → 413/400. Encabezado incorrecto → 400. Un archivo no CSV → 400.
- [x] e2e: una celda `=HYPERLINK(...)` como nombre se rechaza por la regex del nombre.

### Decisiones tomadas

- La rama la había empezado otra sesión de Alexis (API a medias, sin pruebas completas); se retomó por indicación de Juan Camilo, se fusionó `main` y se completó.
- **Rendimiento:** `confirmar` verifica TODA la cadena antes de cada anexo (O(n)); en un lote sería O(n²). `confirmar-lote` verifica la cadena completa **una vez al inicio** del lote (si está comprometida no anexa nada y lo dice) y cada anexo sigue verificando la firma del usuario y creando su sello. Medido con 500 filas (dificultad 2): `preparar-lote` ≈ 0,5 s y `confirmar-lote` ≈ 2,5 s.
- **Bitácora:** una entrada por lote en cada fase: `preparar_lote` (conteo de válidas/inválidas) y `csv` (bloques anexados de N), ambas fuera de transacciones y sin datos personales. No se registran `preparar_bloque` ni `crear_bloque` por fila.
- **Respuesta de `confirmar-lote`:** `{ anexadas: number[], error: string | null }` con 201 aunque falle a mitad: `anexadas` son los índices que sí quedaron en la cadena y `error` el motivo del primer fallo (el resto no se intenta).
- **Archivo:** solo en memoria (Multer sin disco), máx. 200 KB (413), extensión `.csv` y tipo `text/csv` o `application/vnd.ms-excel` (Windows), máx. 500 filas, registros de hasta 4096 bytes; un CSV mal formado (p. ej. comillas sueltas) es 400 para todo el archivo. Las comas dentro de comillas se respetan (`csv-parse`).
- Validación de cada fila con `CrearPersonaDto` (`plainToInstance` + `validate`): las celdas con `=`, `+`, `-`, `@` al inicio del nombre se rechazan por su regex.
- `apps/web/src/api/cliente.ts`: con `FormData` ya no se fuerza `Content-Type: application/json` (cambio mínimo y probado).
- Web: componente `CargaCsv` dentro de Personas (solo registrador con llave aprobada); límite de 200 KB también en el navegador. `docs/ejemplos/personas.csv` tiene 10 filas válidas y 2 inválidas (cédula con letras y nombre `=HYPERLINK`).
- Probado con la API real: CSV de ejemplo → 10 válidas y 2 inválidas, `confirmar-lote` anexa 10, la cadena verifica (11 bloques) y la bitácora muestra una entrada por fase.
