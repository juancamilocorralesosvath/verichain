# H5.1 — Llaves del usuario en el navegador

## Contexto

Diseño §5.3 y §7b "Ciclo de vida de las llaves" (no repudio). **La llave privada nunca sale del navegador sin cifrar.**

## Archivos

- `apps/web/src/cripto/llaves.ts` (lógica pura con WebCrypto) + pruebas (Vitest con entorno que tenga `crypto.subtle`; Node 24 lo trae).
- `apps/web/src/cripto/almacen.ts` (IndexedDB, p. ej. con `idb-keyval`).
- Página/sección "Mi llave" (UI funcional mínima).

## Especificación (no cambiar sin actualizar el diseño)

- Generar: `crypto.subtle.generateKey({ name: 'ECDSA', namedCurve: 'P-256' }, true, ['sign', 'verify'])`.
- Exportar la pública como **SPKI DER en base64**; es lo que se registra en el servidor (H5.2).
- Firmar: `crypto.subtle.sign({ name: 'ECDSA', hash: 'SHA-256' }, privada, new TextEncoder().encode(hashDatosHex))` → base64. WebCrypto produce el formato IEEE-P1363 (64 bytes), que es el que espera el servidor.
- Guardar el par de `CryptoKey` en IndexedDB, asociado al `username`.
- **Respaldo cifrado:** exportar la privada en `pkcs8`. Derivar una llave con PBKDF2-SHA-256 (600 000 iteraciones, salt de 16 bytes) a partir de una contraseña de mínimo 12 caracteres, y cifrar con AES-GCM (IV de 12 bytes). Se descarga un JSON `{ v: 1, kdf: 'PBKDF2-SHA256', iter, salt, iv, ct, spki }` (todo en base64).
- Importar el respaldo: el proceso inverso. Si la contraseña es incorrecta, el error es claro y no rompe la página.

## Criterios de aceptación

- [x] Prueba: generar → firmar → verificar con la pública da true.
- [x] Prueba: respaldo → importar con la contraseña correcta → la llave importada firma y su firma verifica con la pública original.
- [x] Prueba: importar con la contraseña incorrecta lanza un error controlado.
- [x] Prueba de compatibilidad: una firma hecha aquí verifica con `node:crypto` usando `dsaEncoding: 'ieee-p1363'`. Garantiza que el servidor la acepta.
- [x] El JSON de respaldo no contiene la llave privada en claro.

## Notas de traspaso

### Decisiones tomadas

- **Endurecimientos del respaldo** (el formato `{ v, kdf, iter, salt, iv, ct, spki }` no cambia): (1) el encabezado (`v|kdf|iter|salt|spki`) va como datos autenticados (AAD) del AES-GCM, así no se puede manipular sin romper el descifrado; (2) al importar, `iter` debe estar entre 100 000 y 2 000 000, para que un respaldo hostil no cuelgue el navegador; (3) la pública se **deriva de la privada** (JWK → x, y) y debe coincidir con el `spki` del archivo; (4) la contraseña se normaliza a NFC antes de derivar.
- **Errores:** todo fallo de importación (contraseña incorrecta, JSON mal formado, versión o KDF desconocidos, base64 inválido, `iter` fuera de rango) es un `ErrorRespaldo` con mensaje en español; la página sigue viva.
- `firmarHashDatos` exige un SHA-256 en hex minúsculas (64 caracteres): solo firma `hash_datos`.
- **Almacén:** `idb-keyval` (`createStore('verichain','llaves')`, creado al primer uso) guarda el par de `CryptoKey` extraíble por `username`. Las llaves se quedan al salir de sesión.
- **UI "Mi llave":** generar (solo si no hay llave), mostrar SPKI y huella SHA-256, descargar respaldo (contraseña ≥ 12) e importar (pide confirmación si ya hay una llave). **No** registra la pública en el servidor (H5.3).
- **Pruebas:** las de cripto corren en entorno `node` (WebCrypto completo); las del almacén y de la página usan `fake-indexeddb`. `apps/web/test/node-crypto.d.ts` declara lo mínimo de `node:crypto` para la prueba de compatibilidad, sin abrir `@types/node` a `src/`. El `structuredClone` de `CryptoKey` funcionó con `fake-indexeddb` (no hizo falta el plan B).
- **Prueba manual** (API real + Vite, navegador integrado): generar llave, recargar (persiste desde IndexedDB), capturar el respaldo interceptando `URL.createObjectURL` (sin `"d"`, formato v1, `spki` coincide) y registrar esa pública con `POST /api/llaves`: la API respondió 201.
- **Limitación a declarar en el informe:** el `CryptoKey` extraíble en IndexedDB queda al alcance de cualquier script del mismo origen (XSS); es consecuencia de exigir respaldo. Mitigado con CSP de helmet y la regla de no usar `dangerouslySetInnerHTML`.
- `npm audit --omit=dev`: 0 vulnerabilidades; los avisos moderados restantes son la cadena `minimatch`/ESLint (solo desarrollo).
