# H5.1 — Llaves del usuario en el navegador

## Contexto

Diseño §5.3 y §7b "Ciclo de vida de las llaves" (no repudio). **La llave privada nunca sale del navegador sin cifrar.**

## Archivos

- `apps/web/src/cripto/llaves.ts` (lógica pura con WebCrypto) + pruebas (Vitest con entorno que tenga `crypto.subtle`; Node 24 lo trae).
- `apps/web/src/cripto/almacen.ts` (IndexedDB, p. ej. con `idb-keyval`).
- Página/sección "Mi llave" (UI funcional mínima).

## Especificación (no cambiar sin actualizar el diseño)

- Generar: `crypto.subtle.generateKey({ name: 'ECDSA', namedCurve: 'P-256' }, true, ['sign', 'verify'])`.
- Exportar la pública como **SPKI DER en base64**; es lo que se registra en el servidor (H5.2).
- Firmar: `crypto.subtle.sign({ name: 'ECDSA', hash: 'SHA-256' }, privada, new TextEncoder().encode(hashDatosHex))` → base64. WebCrypto produce el formato IEEE-P1363 (64 bytes), que es el que espera el servidor.
- Guardar el par de `CryptoKey` en IndexedDB, asociado al `username`.
- **Respaldo cifrado:** exportar la privada en `pkcs8`. Derivar una llave con PBKDF2-SHA-256 (600 000 iteraciones, salt de 16 bytes) a partir de una contraseña de mínimo 12 caracteres, y cifrar con AES-GCM (IV de 12 bytes). Se descarga un JSON `{ v: 1, kdf: 'PBKDF2-SHA256', iter, salt, iv, ct, spki }` (todo en base64).
- Importar el respaldo: el proceso inverso. Si la contraseña es incorrecta, el error es claro y no rompe la página.

## Criterios de aceptación

- [ ] Prueba: generar → firmar → verificar con la pública da true.
- [ ] Prueba: respaldo → importar con la contraseña correcta → la llave importada firma y su firma verifica con la pública original.
- [ ] Prueba: importar con la contraseña incorrecta lanza un error controlado.
- [ ] Prueba de compatibilidad: una firma hecha aquí verifica con `node:crypto` usando `dsaEncoding: 'ieee-p1363'`. Garantiza que el servidor la acepta.
- [ ] El JSON de respaldo no contiene la llave privada en claro.
