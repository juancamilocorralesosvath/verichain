# H8.1 — CLI verificador independiente

## Contexto

Diseño §5.9. Mensaje para la sustentación: "no hace falta confiar en el servidor".

## Archivos

`tools/verificador/**` (reemplaza el README placeholder). Paquete `@bc/verificador` con `bin: { verificador }`.

## Especificación

- Uso: `verificador <cadena.json> --server-key <server-public.pem> [--json]`.
- Lee los archivos, `parsearExportacion`, convierte el PEM a SPKI DER b64 y llama a `verificarCadena` con un `VerificadorFirma` de `node:crypto` (igual al de H2.3, pero sin importar la API).
- Si la huella del PEM fijado ≠ `huella_llave_servidor` del JSON → advertencia visible. **Siempre** se usa la llave fijada.
- Salida legible en español: una tabla por bloque con ✔/✘ por chequeo, el sello y el veredicto final. Con `--json`, el `ReporteCadena` crudo.
- Código de salida: 0 si es válida, 1 si no, 2 si hay un error de uso o de archivo.
- Solo usa dependencias mínimas (`node:util parseArgs` en lugar de librerías de CLI).

## Criterios de aceptación

- [x] Pruebas: con fixtures en `tools/verificador/test/fixtures/` (una cadena válida + su PEM, una alterada y una con un PEM distinto), los códigos de salida son 0, 1 y 1, y aparece la advertencia de huella en el tercer caso.
- [x] `npx verificador` funciona desde la raíz después de `npm run build`.

## Verificación

```bash
npm run build && npm run test -w @bc/verificador && npm run check
```

## Notas de traspaso

### Decisiones tomadas

- **Paquete `@bc/verificador`** (`bin: verificador` → `dist/cli.js`, ESM): solo depende de `@bc/core` y de `node:util parseArgs`/`node:crypto`; no importa nada de la API. `ejecutar(argv, io)` contiene toda la lógica y no toca `process` (por eso se prueba en proceso); `cli.ts` solo la conecta a stdout/stderr y al código de salida.
- **Uso:** `verificador <cadena.json> --server-key <server-public.pem> [--json]` (`-k`, `-h/--help`). Lee la exportación con `parsearExportacion`, convierte el PEM a SPKI base64 y verifica con `aOpcionesVerificacion`, que obliga a pasar la llave fijada: **siempre se usa la fijada**, nunca la del JSON.
- **Advertencia de huella:** si la huella de la llave fijada ≠ `huella_llave_servidor` del archivo, se imprime una advertencia en **stderr** (así no rompe `--json`) con ambas huellas; el resultado sigue calculándose con la fijada (en el fixture con otra llave el sello falla y el código es 1).
- **Salida:** informe legible en español (tabla por bloque con ✔/✘/— por chequeo, motivos por bloque, sello y veredicto, con la dificultad "según el archivo" a la vista) o, con `--json`, el `ReporteCadena` crudo. **Códigos de salida:** 0 íntegra, 1 comprometida, 2 error de uso o de archivo (sin argumentos, falta `--server-key`, opción desconocida, archivo ilegible, JSON inválido, formato desconocido, PEM que no es una llave P-256).
- **Sin sello = comprometida,** igual que en la API: si el archivo no trae el sello el CLI marca `sello: falla` (si no, quitar el sello silenciaría la detección).
- **Fixtures** reales en `tools/verificador/test/fixtures/` (cadena válida, alterada con el nombre de la persona del bloque 2 cambiado, `server-public.pem` y `otra-llave-public.pem`), generados por `npm run fixtures -w @bc/verificador`; las llaves privadas se descartan y solo se versionan públicas (el `.gitignore` ya exceptúa `test/fixtures/**/*.pem`). Casos: 0, 1 y 1 (con advertencia) más los errores (2), en proceso y con el binario compilado.
- `npx verificador` funciona desde la raíz tras `npm run build` y `npm install` (el workspace crea el enlace en `node_modules/.bin`); probado a mano con los tres casos. `pretest` compila `@bc/core` y el paquete.
- La dificultad se toma del archivo (se muestra en el informe); la protección fuerte contra reescrituras es el sello, no el PoW (§5.5).
