# H1.4 — Verificación completa de la cadena

## Contexto

Diseño §4 "Funciones", §5.4, §5.7 y §5.8. Es **la única** implementación de la verificación: la usan la API (H2.3), el CLI (H8.1) y la página del verificador (H8.2). Por eso no puede depender de Node: la verificación de firmas se **inyecta** como función.

## Especificación (no cambiar sin actualizar el diseño)

```ts
export interface BloqueCadena {
  indice: number; // 0 = génesis
  hash_datos: string; // guardado
  nonce: number;
  hash_anterior: string;
  hash_cadena: string;
  firma_usuario: string | null; // base64 de la firma ECDSA P-256 en formato IEEE-P1363 (r||s, 64 bytes); null en génesis
  llave_id: number | null;
  persona: FilaPersona | null; // fila ACTUAL de la tabla personas (null en génesis)
}
export interface Sello {
  indice: number;
  hash_cadena: string;
  firma: string;
} // firma base64 P1363
// Mensaje firmado por el usuario: los bytes ASCII del string hex `hash_datos`.
// Mensaje del sello: los bytes ASCII de `${indice}:${hash_cadena}`.
export type VerificadorFirma = (
  llavePublicaSpkiB64: string,
  mensaje: string,
  firmaB64: string,
) => Promise<boolean>;

export interface OpcionesVerificacion {
  dificultad: number;
  llavesUsuarios: Record<number, string>; // llave_id → llave pública SPKI DER en base64
  verificarFirma?: VerificadorFirma; // si falta: chequeos de firma = 'no-aplica'
  sello?: Sello | null;
  llavePublicaServidor?: string; // SPKI DER base64
}
export type EstadoChequeo = 'ok' | 'falla' | 'no-aplica';
export interface ReporteBloque {
  indice: number;
  chequeos: {
    hashDatos: EstadoChequeo;
    enlace: EstadoChequeo;
    hashCadena: EstadoChequeo;
    pow: EstadoChequeo;
    firmaUsuario: EstadoChequeo;
  };
  motivos: string[]; // en español claro, p. ej. "Los datos de la persona no coinciden con el hash guardado"
}
export interface ReporteCadena {
  valida: boolean;
  primerBloqueRoto: number | null;
  bloques: ReporteBloque[];
  sello: { estado: EstadoChequeo; motivos: string[] };
  totalBloques: number;
}
export function verificarCadena(
  bloques: BloqueCadena[],
  opciones: OpcionesVerificacion,
): Promise<ReporteCadena>;
```

Reglas por bloque `i` (los bloques llegan ordenados por `indice`):

- **Índices:** deben ser 0..n-1 consecutivos. Un hueco o un desorden es una falla en `enlace`.
- **hashDatos:** en el génesis se compara con `HASH_DATOS_GENESIS`. En los demás, `calcularHashDatos(persona)` debe ser igual al `hash_datos` guardado. Si `persona` es null fuera del génesis, falla.
- **enlace:** el génesis tiene `hash_anterior === HASH_CERO`. En los demás, `hash_anterior === bloques[i-1].hash_cadena` (el guardado).
- **hashCadena:** `calcularHashCadena(hash_anterior, hash_datos_recalculado, nonce) === hash_cadena`.
- **pow:** `cumpleDificultad(hash_cadena, dificultad)`.
- **firmaUsuario:** `no-aplica` en el génesis o si no hay `verificarFirma`. Si no, falla si falta la firma, si la llave no existe o si la firma no es válida.

Sello: `no-aplica` si no hay `sello` o no hay `verificarFirma`/`llavePublicaServidor`. Si no, falla si la firma no es válida **o** si `sello.indice`/`sello.hash_cadena` no coinciden con el **último** bloque (así se detecta el truncamiento).

`valida` = ningún chequeo en `falla`. `primerBloqueRoto` = el menor índice con alguna falla (o null).

## Criterios de aceptación

Las pruebas construyen una cadena válida de 5 bloques (dificultad 2) con llaves ECDSA reales generadas en el test con `crypto.subtle` (permitido en tests). Verifican:

- [ ] Una cadena íntegra da `valida: true`, con todo en `ok`.
- [ ] **Ataque 1:** cambiar `persona.nombre` del bloque 2 → falla `hashDatos` y `hashCadena` en el 2; `primerBloqueRoto = 2`.
- [ ] **Ataque 2:** cambiar un carácter de `telefono_cifrado` → falla `hashDatos`.
- [ ] **Ataque 3:** cambiar un dato y **recalcular** `hash_datos`, re-minar y reencadenar todos los bloques siguientes → los hashes, el enlace y el PoW quedan `ok`, pero falla `firmaUsuario` en el bloque tocado y falla el sello.
- [ ] **Ataque 4:** borrar el último bloque → todos los bloques en `ok`, pero el sello falla con el motivo de truncamiento.
- [ ] **Ataque 5:** intercambiar los bloques 2 y 3 (con sus índices) → falla `enlace`.
- [ ] Sin `verificarFirma`, los chequeos de firma y de sello quedan en `no-aplica` y la cadena íntegra sigue siendo válida.
- [ ] Los motivos están en español y nombran el campo o el chequeo.
