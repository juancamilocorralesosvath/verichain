# H3.3 — Gestión de usuarios (admin)

## Especificación

- Solo admin:
  - `GET /api/usuarios`
  - `POST /api/usuarios { username, password, rol }`
  - `PATCH /api/usuarios/:id { activo?, rol? }`
- Política de contraseña: mínimo 12 caracteres, que no sea igual al username. Validar en el DTO.
- No se borran usuarios (quedan referenciados en bloques y bitácora): solo se desactivan. Un usuario inactivo no puede iniciar sesión, y si ya tiene un JWT, este se rechaza en la siguiente petición (el guard consulta `activo`).
- Las respuestas **nunca** incluyen `password_hash`.
- Un admin no puede desactivarse a sí mismo ni quitarse el rol de admin.

## Criterios de aceptación

- [x] e2e: un registrador o auditor que llama a cualquiera de estos endpoints → 403.
- [x] e2e: contraseña corta → 400.
- [x] e2e: desactivar un usuario con sesión abierta → su siguiente petición da 401.
- [x] Ninguna respuesta incluye `password_hash` (prueba).

## Notas de traspaso

### Decisiones tomadas

- **`UsuariosModule`** (`apps/api/src/usuarios`), todo `@Roles('admin')` a nivel de clase: `GET /api/usuarios`, `POST /api/usuarios { username, password, rol }` y `PATCH /api/usuarios/:id { activo?, rol? }`. **No hay DELETE** (404): los usuarios quedan referenciados en bloques y bitácora, solo se desactivan.
- **Política en el DTO:** `username` 3–50 con `[A-Za-z0-9._-]`; `password` de **12 a 128** caracteres (el tope evita abusar de argon2) y **distinta del username** sin importar mayúsculas (decorador propio `@NoIgualA`); `rol` ∈ admin/registrador/auditor; el `ValidationPipe` global rechaza campos extra. `PATCH` exige al menos un campo (`activo` booleano o `rol`) y no admite cambiar contraseña (queda fuera de alcance). Contraseña con **argon2id** como en el seed.
- **Respuestas** con `select` explícito `{ id, username, rol, activo, creado_en }`: `password_hash` nunca se lee de la BD para responder; una prueba comprueba que ni crear, listar ni editar contienen `password`, `argon2` o `hash`. Usuario repetido → 409 `Registro duplicado`; id inexistente → 404; id no numérico → 400.
- **Reglas del admin:** no puede desactivarse ni quitarse el rol de admin (403 `No puedes desactivarte ni quitarte el rol de admin`), así siempre queda al menos un admin; sí puede cambiar a otros (incluso ascenderlos a admin).
- **Sesiones:** desactivar o cambiar el rol de un usuario invalida su sesión abierta en su **siguiente petición** (`AuthService.autenticar` consulta `activo` y compara el rol del token con el de la BD), y un usuario inactivo no puede iniciar sesión; reactivarlo le devuelve el acceso. Todo probado con sesiones reales.
- **Bitácora:** `usuario_crear` (`usuario <nombre> (<rol>)`) y `usuario_editar` (`usuario <nombre>: activo=false, rol=auditor`), nunca la contraseña.
- **Pruebas:** e2e de usuarios (listar, crear y login, argon2id, 10 casos de 400, 409, desactivar con sesión abierta, cambio de rol, reglas del admin, PATCH inválidos, permisos —registrador y auditor 403 en los tres, sin sesión 401—, sin DELETE y bitácora); fila `GET /api/usuarios` en la matriz de `roles.e2e`, cuya prueba genérica de rutas ahora también ejercita `PATCH`. El login está limitado a 5 por minuto por IP: las pruebas que necesitan varios logins lo tienen en cuenta.
- **Prueba manual** con la API real: crear un usuario, contraseña corta (400), login, desactivarlo (su sesión da 401) y el admin intentando desactivarse (403).
