# H5.4 — Sello del servidor y bloqueo de cadena comprometida

## Contexto

Diseño §5.4 y §7b "Sello del servidor". Detecta "alterar y recalcular todo" y el truncamiento. Además impide que un anexo nuevo "lave" un ataque.

## Especificación

- Script `npm run llaves:servidor -w @bc/api`: genera ECDSA P-256 en `secrets/server-signing-key.pem` (PKCS8, permisos 600) y `secrets/server-public.pem`. Si ya existen, no las sobrescribe.
- Al arrancar, la API lee la llave de `SERVER_SIGNING_KEY_PATH`. Si no existe, no arranca y muestra un mensaje que indica el script.
- Modelo `Sello { id, indice, hash_cadena, firma, creado_en }` (histórico; el vigente es el de mayor `id`).
- Después de crear el génesis y después de **cada** anexo (en la misma transacción): firmar los bytes ASCII de `${indice}:${hash_cadena}` con `dsaEncoding: 'ieee-p1363'` y guardar el sello.
- **Antes** de cada anexo: correr `verificarCadena` completa (firmas + sello vigente). Si no es válida → 409 `{ mensaje: 'Cadena comprometida: restaure antes de continuar' }` y no se escribe nada.
- `GET /api/cadena/verificar` ahora pasa también `sello` y `llavePublicaServidor`.
- `GET /api/cadena/llave-servidor` (público): `{ pem, huella_sha256 }`. La huella es el SHA-256 hex del SPKI DER.

## Criterios de aceptación

- [x] e2e: la cadena con sello verifica con `sello.estado: 'ok'`.
- [x] e2e: borrar el último bloque y su persona → `valida: false` con el motivo de truncamiento.
- [x] e2e: alterar un dato y recalcular hashes y PoW de todos los bloques (con las funciones de core, en el test) → falla la firma del usuario y falla el sello.
- [x] e2e: con la cadena alterada, `confirmar` → 409 y la cantidad de bloques no cambia.
- [x] La llave privada no aparece en ninguna respuesta ni en los logs.

## Verificación

```bash
npm run test -w @bc/api && npm run check
```

## Notas de traspaso

### Decisiones tomadas

- **Sin re-sello automático al arrancar:** si la cadena ya existe y no tiene sellos, el servidor **no** los crea. Un atacante que truncara la cadena y borrara la tabla de sellos conseguiría que el servidor "bendijera" el estado manipulado. Una BD de desarrollo creada antes de H5.4 queda comprometida hasta resetearla (borrar `apps/api/data/`); "Restaurar demo" (H6.2) cubrirá ese caso.
- **Sin ningún sello = comprometida:** el core devuelve `no-aplica` cuando no recibe sello; la API lo convierte en `sello: falla` y `valida: false` (si no, borrar la tabla de sellos silenciaría la detección). El core no cambió. Borrar solo el sello vigente también se detecta (el sello viejo no coincide con el último bloque).
- **Sello en la misma transacción** que el anexo; el génesis y su sello se crean juntos. Antes de cada anexo (`confirmar`, ya dentro de la cola y tras validar borrador, llave y firma) se corre la verificación completa; si no es válida → 409 con el mensaje exacto de la historia y no se escribe nada (el borrador no se consume). Coste O(n) por anexo: aceptable para la demo, a revisar con la carga CSV (H7.1).
- **Llave del servidor:** `FirmaServidorService` la lee al arrancar (`SERVER_SIGNING_KEY_PATH`, relativa a `apps/api`), exige EC P-256 y, si falta o no sirve, la API no arranca con un error que nombra `npm run llaves:servidor -w @bc/api`. La privada vive en un campo privado (`#`), nunca se serializa ni se registra; una prueba comprueba que no aparece en respuestas ni en stdout/stderr (incluido el camino de error).
- **Script** `scripts/llaves-servidor.mjs` autocontenido (sin build): privada PKCS8 con modo 600 en una carpeta 700, pública SPKI al lado, escritura con `wx` (nunca sobrescribe); si falta solo una de las dos, falla sin tocar nada.
- **`GET /api/cadena/llave-servidor`** es público y devuelve solo `{ pem, huella_sha256 }`. La prueba genérica de rutas públicas de `roles.e2e` ahora lista esta ruta.
- **Pruebas:** `globalSetup` genera una llave de servidor de prueba en un archivo temporal y `crearBdTemporal()` fija `SERVER_SIGNING_KEY_PATH`. Se ajustó `verificar.e2e` (el sello pasa de `no-aplica` a `ok`) y `roles.e2e` (ruta pública nueva).
- **Prueba manual** (API real, BD y llave temporales): arrancar sin llave falla con el mensaje del script; el script real crea la privada con permisos 600 y no sobrescribe; con 2 anexos firmados `verificar` da `sello: ok`; al borrar el último bloque directamente en SQLite el reporte marca `valida: false` con el motivo de truncamiento (los bloques restantes siguen bien) y `confirmar` responde 409 `Cadena comprometida: restaure antes de continuar`.
- **Riesgo aceptado (del diseño):** el rollback completo (volver a una cadena y sellos antiguos coherentes) no se detecta; "Restaurar demo" es justamente ese rollback.
- **Aviso:** tras mezclar hay que generar la llave local con `npm run llaves:servidor -w @bc/api` y empezar con BD nueva.
