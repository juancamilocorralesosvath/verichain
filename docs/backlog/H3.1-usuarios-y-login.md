# H3.1 — Usuarios, contraseñas y login

## Contexto

Diseño §5.2 (Unidad 3: autenticación). Se puede hacer en paralelo con H2.2/H2.3.

## Especificación

- Modelo Prisma `Usuario { id, username @unique, password_hash, rol ('admin'|'registrador'|'auditor'), activo Boolean, creado_en }`.
- Hash con **argon2id** (paquete `argon2`), con los parámetros por defecto de la librería o más fuertes.
- _Seed_ idempotente: crea el admin con `ADMIN_USERNAME`/`ADMIN_PASSWORD` de `.env`. Si `ADMIN_PASSWORD` está vacío o tiene menos de 12 caracteres, falla con un mensaje claro.
- `POST /api/auth/login { username, password }`:
  - Si es correcto: JWT (HS256, `JWT_SECRET`, expira en `JWT_EXPIRES_IN`) con `{ sub, username, rol }` en la cookie `sesion` (`httpOnly`, `sameSite: 'strict'`, `secure` cuando `NODE_ENV=production`, `path: '/api'`). Responde `{ username, rol }`.
  - Si falla: 401 con el **mismo mensaje** para usuario inexistente y para contraseña incorrecta. Calcula un hash argon2 ficticio cuando el usuario no existe, para no filtrar su existencia por el tiempo de respuesta.
  - Throttler específico: máximo 5 intentos por minuto por IP en esta ruta.
- `POST /api/auth/logout` borra la cookie. `GET /api/auth/yo` devuelve el usuario actual o 401.
- `JwtAuthGuard` lee la cookie (no el header Authorization). `JWT_SECRET` vacío → la app no arranca.
- Hasta H7.2 no hay bitácora: deja un `TODO(H7.2)` en el login exitoso y en el fallido.

## Criterios de aceptación

- [ ] e2e: login correcto → cookie con los atributos `HttpOnly` y `SameSite=Strict`, y `GET /auth/yo` devuelve el rol.
- [ ] e2e: contraseña mala y usuario inexistente → 401 con un body idéntico.
- [ ] e2e: el sexto intento en un minuto → 429.
- [ ] La BD nunca guarda la contraseña en claro (la prueba lee la fila y verifica que empieza con `$argon2id$`).
- [ ] Correr el seed dos veces no duplica al admin.
