# H5.3 — Crear bloques firmados: preparar → firmar → confirmar

## Contexto

Diseño §5.3. El servidor **no puede** firmar por el usuario. Esta historia **reemplaza** `POST /api/personas` de H2.2 (bórralo, junto con sus pruebas, que se reescriben aquí).

## Especificación

- Modelo `Borrador { id (uuid), usuario_id, fila_json, hash_datos, expira_en }`.
- `POST /api/bloques/preparar` (registrador) con el body de `CrearPersonaDto`:
  - Valida y normaliza, rechaza cédula duplicada (409), cifra y arma la `FilaPersona` con `creado_en` y `creado_por`.
  - Calcula `hash_datos`, guarda el borrador (expira en 5 min) y responde `{ borrador_id, hash_datos }`.
- `POST /api/bloques/confirmar { borrador_id, llave_id, firma_b64 }` (registrador):
  1. El borrador existe, es del mismo usuario y no ha expirado. Si no → 404/410.
  2. La llave es del usuario y está `aprobada`. Si no → 403.
  3. La firma verifica sobre los bytes ASCII de `hash_datos` (usa el `VerificadorFirma` de H2.3). Si no → 400 "firma inválida".
  4. En una transacción: revisar otra vez la cédula única, leer el último bloque, minar, insertar la persona y el bloque (con `firma_usuario` y `llave_id`) y borrar el borrador.
- Limpieza de borradores expirados al preparar (o con un intervalo).
- La web (página Personas, H9.2) usa este flujo: preparar → `firmar(hash_datos)` con la llave de IndexedDB → confirmar. Si el usuario no tiene llave aprobada, la UI lo explica y lo lleva a "Mi llave".
- `GET /api/cadena/verificar` ahora pasa `verificarFirma` y `llavesUsuarios` (sin sello todavía).

## Criterios de aceptación

- [x] e2e completo con una llave ECDSA generada en el test: preparar → firmar → confirmar → la cadena verifica con `firmaUsuario: 'ok'`.
- [x] e2e: una firma de otra llave → 400. El borrador de otro usuario → 404. Un borrador expirado (con reloj simulado) → 410. Una llave pendiente → 403.
- [x] e2e: reutilizar un `borrador_id` ya confirmado → 404 (no se puede repetir).
- [x] Manual: desde la web, un registrador con llave aprobada crea una persona y la ve en la cadena.

## Notas de traspaso

### Decisiones tomadas

- **Borrador:** `fila_json` guarda la fila **ya cifrada** (el hash incluye el texto cifrado con IV aleatorio, no se puede recalcular después). Al confirmar se recalcula `hash_datos` de esa fila y se exige que coincida con el guardado. Expira en 5 minutos; `preparar` borra los vencidos y un borrador expirado que se intenta confirmar da 410 y se elimina.
- **`confirmar` completo dentro de la cola de anexos:** así un mismo borrador no se puede confirmar dos veces a la vez (una gana, la otra recibe 404) ni dos borradores con la misma cédula pasan la revisión final (el segundo recibe 409).
- **404 también para el borrador de otro usuario** (no revela que existe). Llave inexistente, de otro usuario o no `aprobada` → 403 `Llave no autorizada`. Firma inválida → 400 `Firma inválida` y el borrador sigue sirviendo con la firma correcta.
- **`CadenaService`:** se quitó `agregarPersona`; ahora expone `serializar`, `construirFila` y `anexarBloqueTx`. `POST /api/personas` ya no existe (404); queda solo `GET /api/personas`. `confirmar` responde `{ indice, persona_id, hash_datos, hash_cadena }`.
- **`GET /api/cadena/verificar`** pasa `verificarFirma` (`verificarFirmaNode`) y `llavesUsuarios`; el sello sigue sin aplicar (H5.4). Un bloque sin firma ahora falla en `firmaUsuario`: solo afecta a BDs de desarrollo creadas antes de H5.3 (hay que borrar `apps/api/data/`).
- **Hueco de H5.1 resuelto aquí:** "Mi llave" muestra el estado de la llave en el servidor y tiene el botón **Registrar en el servidor** (`POST /api/llaves`). La **aprobación del admin** sigue siendo por `curl` hasta H9.4.
- **Personas (web):** el formulario solo aparece con una llave local **registrada y aprobada** (se comparan los SPKI de IndexedDB y `/api/llaves/mias`); si no, explica qué falta y enlaza a "Mi llave". El flujo es validar → preparar → firmar → confirmar → recargar.
- **Archivos de otras historias tocados:** `roles.e2e.test.ts` (H3.2: filas de la matriz y prueba del creador), `verificar.e2e.test.ts` (H2.3: firmas `ok`) y `personas.e2e.test.ts` (H2.2, reescrito); en la web `personas.test.tsx` (H9.2) y `mi-llave.test.tsx` (H5.1). Las firmas ECDSA no son deterministas: las pruebas comparan contra la firma enviada, no recalculada.
- **Prueba manual** (API real + Vite, BD temporal, navegador integrado): con la llave sin registrar la UI explica y enlaza; se registró desde "Mi llave" (queda pendiente); el admin la aprobó por `curl`; se creó una persona desde la web y apareció en la tabla y en Cadena (firmante `registrador1`, llave 1); `GET /api/cadena/verificar` dio `valida: true` con `firmaUsuario: 'ok'`.
