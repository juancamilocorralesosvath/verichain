# H7.2 — Bitácora de auditoría encadenada

## Contexto

Diseño §5.10. Registra quién hizo qué. Va encadenada con hash para que también sea a prueba de manipulación.

## Especificación

- En `@bc/core` agrega `bitacora.ts`:
  ```ts
  export const CAMPOS_BITACORA = [
    'fecha',
    'usuario',
    'accion',
    'resultado',
    'ip',
    'detalle',
  ] as const;
  export type EntradaBitacora = Record<(typeof CAMPOS_BITACORA)[number], string>;
  export function hashEntradaBitacora(hashAnterior: string, e: EntradaBitacora): string;
  //   = sha256Hex(hashAnterior + JSON.stringify(e en el orden de CAMPOS_BITACORA))
  export function verificarBitacora(entradas: (EntradaBitacora & { hash: string })[]): {
    valida: boolean;
    primeraRota: number | null;
  };
  ```
  La primera entrada usa `HASH_CERO` como anterior. Incluye pruebas en core.
- Modelo `Bitacora { id, fecha, usuario, accion, resultado ('ok'|'fallo'), ip, detalle, hash }`. Es _append-only_: el servicio solo expone `registrar()`.
- `BitacoraService.registrar(...)` se llama en todos los `TODO(H7.2)` del código (búscalos con `grep -rn "TODO(H7.2)"`) y además en: crear bloque, verificar, exportar, ataques, restaurar, snapshot, crear/editar usuario y llaves.
  - `usuario` = username, o `'-'` si no hay sesión.
  - `detalle` = texto corto **sin datos personales ni secretos** (p. ej. `"bloque 7"`, nunca la contraseña ni el teléfono).
- `GET /api/bitacora?pagina=` (admin y auditor) → `{ entradas, verificacion: verificarBitacora(...) }`.

## Criterios de aceptación

- [x] Pruebas de core: una bitácora íntegra es válida; alterar el `detalle` de una entrada o borrar una del medio → inválida, con la posición.
- [x] e2e: un login fallido y uno exitoso → 2 entradas con el resultado correcto, y la contraseña no aparece en ningún campo.

## Notas de traspaso

### Decisiones tomadas

- **core** (`bitacora.ts`): `CAMPOS_BITACORA`, `EntradaBitacora`, `hashEntradaBitacora(anterior, entrada)` (= `sha256Hex(anterior + JSON.stringify` de la entrada en el orden canónico; valida que `anterior` sea 64 hex y que los 6 campos sean strings) y `verificarBitacora(entradas)` → `{ valida, primeraRota }` con la posición (desde 0) de la primera entrada que no cuadra; la primera encadena con `HASH_CERO`. Alterar el detalle, borrar una del medio o la primera, intercambiar dos o cambiar un hash guardado se detecta. **Límite conocido:** borrar entradas del **final** no se detecta con el encadenamiento solo (la bitácora no tiene sello).
- **API:** modelo `Bitacora` (+ migración) y `BitacoraService` (módulo global): solo `registrar()` y lectura (append-only). `registrar` usa su **propia cola** (cada entrada lee el último hash y encadena) y **nunca debe llamarse dentro de un `$transaction` interactivo** (SQLite tiene una sola conexión y se bloquearía): todos los puntos de la app lo llaman después de que la transacción termina. Si registrar falla, se anota en el `Logger` y la operación ya hecha no se revierte.
- **Qué se registra** (acción → quién): `login` / `login_fallido`, `preparar_bloque`, `crear_bloque` (ok y fallo con el motivo genérico), `llave_registrar` / `llave_aprobar` / `llave_rechazar`, `verificar`, `exportar`, `ataque` (ok y fallo), `snapshot` y `restaurar`. `usuario` es el username o `-` sin sesión; la IP sale de `req.ip`. Los `TODO(H7.2)` desaparecieron (`grep` sin resultados).
- **Login fallido:** `usuario = '-'` y detalle genérico `credenciales inválidas`: no se guarda lo escrito en el campo usuario porque a menudo es una contraseña. **Sanidad de campos:** `registrar` quita saltos de línea y caracteres de control y acota el largo (usuario 100, acción 50, IP 64, detalle 200). `detalle` nunca lleva datos personales ni secretos (p. ej. `bloque 7`, `llave 3 versión 2`); una prueba busca la cédula, dirección y teléfono del test y las contraseñas dentro de todo lo guardado y devuelto.
- **`GET /api/bitacora?pagina=`** (admin y auditor; registrador 403, sin sesión 401): `{ entradas, pagina, totalPaginas, total, verificacion }`. Páginas de 50 con **las más recientes primero**; la `verificacion` se calcula sobre **toda** la cadena de la bitácora, no solo la página. `pagina` inválida (0 o no numérica) → 400; fuera de rango → lista vacía.
- **"Restaurar demo" también restaura la bitácora** (es un rollback completo de la BD): las entradas posteriores al snapshot desaparecen y la entrada `restaurar` se encadena sobre ese estado, de modo que la bitácora sigue siendo válida (probado). Se anota para la sustentación junto con el riesgo de rollback.
- **Pruebas:** core (102 en total), e2e de la bitácora (login fallido + exitoso con la contraseña ausente, hash encadenado fila a fila, cada acción, fallo de firma, llaves, permisos, alterar y borrar entradas, paginación de 120 entradas, limpieza de campos, página inválida) y un caso en `demo.e2e` (ataque, snapshot y restaurar). Se añadió la fila de la matriz en `roles.e2e`. **Prueba manual** con la API real: login con clave mala (401) y correcto (201) y una verificación dejaron 3 entradas válidas, y la contraseña mala no aparece en la BD.
