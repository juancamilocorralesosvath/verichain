# H9.2 — Páginas Personas y Cadena

## Especificación

- **Personas:**
  - Tabla con lo que devuelve `GET /api/personas`. Muestra `***` o el dato según el rol; las filas con `integra: false` van marcadas.
  - Formulario de creación (solo registrador) con validación en el cliente que replica las reglas del DTO. **La validación real sigue siendo la del servidor.**
  - Antes de H5.3 usa `POST /api/personas`; H5.3 cambia esto al flujo firmado.
- **Cadena:**
  - Lista de bloques en orden: índice, fecha, `hash_anterior` (abreviado y con tooltip para verlo completo), `hash_datos`, nonce, `hash_cadena`, firmante y `llave_id`.
  - El génesis va distinguido.
- Los estados de carga, error y vacío están cubiertos.

## Criterios de aceptación

- [x] Prueba: el formulario muestra un error con una cédula inválida y no envía la petición.
- [x] Prueba: la tabla renderiza `***` para el auditor.
- [x] Manual con la API corriendo: crear una persona → aparece en la tabla y como bloque nuevo en la Cadena.

## Notas de traspaso

### Decisiones tomadas

- **Contrato tolerante:** la web se escribe contra el contrato de H4.2 (`direccion`, `telefono`, `integra`), pero acepta la forma actual de la API (`direccion_cifrada`...): si `direccion`/`telefono` no vienen se muestra `***`. Por eso hoy, incluso el registrador ve `***` hasta que se haga H4.2; no hay que reescribir nada entonces.
- **`***` forzado en el cliente:** solo el registrador ve dirección y teléfono; cualquier otro rol ve `***` aunque el servidor enviara los datos. Un valor `null` (fallo de descifrado) se muestra como `—`.
- **Filas `integra: false`:** `data-integra="false"` y la marca "Dato corrupto". Una fila sin `integra` se considera íntegra.
- **Firmante en Cadena:** `/api/cadena` no lo trae; se une `persona_id → creado_por` desde `/api/personas` para registrador y auditor. El admin recibe 403 en personas, así que no se le pide y ve `—`. Mejora futura: que la API incluya el firmante en `/api/cadena`.
- **Validación del cliente** (`src/validacion.ts`): replica el DTO y solo evita el viaje; la real es la del servidor. Normaliza con trim y NFC igual que la API.
- Las funciones `listarPersonas` y `listarCadena` lanzan "Respuesta inesperada" si la API no devuelve una lista, para mostrar un error en vez de romper la página.
- **Archivo de otra historia modificado:** `test/app.test.tsx` (H9.1): su `fetch` simulado devolvía el usuario para todas las URL; ahora solo `/auth/yo` devuelve el usuario y el resto devuelve `[]`, porque las páginas Personas y Cadena también piden datos.
- **Prueba manual** (API real + Vite con proxy, BD temporal, navegador integrado): cédula inválida → error en el formulario y sin POST; con datos válidos la persona aparece en la tabla y como bloque 1 en Cadena, con el génesis distinguido, hashes abreviados y firmante `registrador1`.
