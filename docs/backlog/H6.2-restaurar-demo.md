# H6.2 — Snapshot y "Restaurar demo"

## Contexto

Diseño §5.7 y §7b (restaurar es, conceptualmente, el _rollback_ aceptado como riesgo; se explica en la sustentación).

## Especificación

- Solo con `DEMO_MODE` y para admin:
  - `POST /api/demo/snapshot`: guarda una copia de la BD SQLite en `apps/api/data/snapshot.db`. Usa `VACUUM INTO` o la API de backup de better-sqlite3; no copies el archivo con la BD abierta.
  - `POST /api/demo/restaurar`: reemplaza el contenido actual con el snapshot de forma segura (sin dejar conexiones de Prisma con datos viejos) y responde el resultado de verificar.
- Si no hay snapshot → 409 con un mensaje claro.
- README del API, sección **"Ataque manual con sqlite3"**:
  - Instalar `sqlite3` (`sudo apt install sqlite3`).
  - Comando de ejemplo: `UPDATE Persona SET nombre='Mallory' WHERE id=1;`.
  - Luego verificar en la UI.

## Criterios de aceptación

- [x] e2e: snapshot → ataque → restaurar → `valida: true` y la cantidad de bloques es igual a la original.
- [x] e2e: restaurar sin snapshot → 409.
- [x] La guía manual está en el README y se probó a mano una vez (anótalo en las notas).

## Notas de traspaso

### Decisiones tomadas

- **`DemoModule`** (solo con `DEMO_MODE=true`, admin): `POST /api/demo/snapshot` y `POST /api/demo/restaurar`; sin DEMO_MODE las rutas no existen (404). Ambas van por la cola de anexos.
- **Copia con la API de backup de SQLite** (`better-sqlite3`, ahora dependencia explícita de `@bc/api`, con `@types/better-sqlite3`): el snapshot se escribe en `snapshot.db` junto a la BD (reemplaza el anterior) y restaurar copia el snapshot **dentro** de la BD con la misma API. SQLite coordina con la conexión abierta de Prisma: no se copia el archivo a mano y Prisma no queda con datos viejos (una prueba anexa bloques después de restaurar).
- `snapshot` responde `{ guardado: true, bloques }`; `restaurar` responde `{ restaurado: true, verificacion: <reporte de verificar> }`. Sin snapshot → 409 `No hay snapshot: guarda uno antes de restaurar` y la BD no cambia.
- **Los usuarios y sus sesiones también vuelven al estado del snapshot** (es un rollback completo de la BD): conviene hacer el snapshot cuando ya existan todos los usuarios de la demo. Es el rollback que el diseño §7b acepta como riesgo.
- **Guía manual** en `apps/api/README.md` ("Ataque manual con sqlite3"). **Probada a mano** con la API real en modo demo: cadena íntegra → snapshot → `UPDATE Persona SET nombre='Mallory' WHERE id=1;` directo en la BD → `verificar` da `valida: false` y `primerBloqueRoto: 1` → restaurar → `valida: true` con los mismos 3 bloques.
