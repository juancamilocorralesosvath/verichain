# H6.2 — Snapshot y "Restaurar demo"

## Contexto

Diseño §5.7 y §7b (restaurar es, conceptualmente, el _rollback_ aceptado como riesgo; se explica en la sustentación).

## Especificación

- Solo con `DEMO_MODE` y para admin:
  - `POST /api/demo/snapshot`: guarda una copia de la BD SQLite en `apps/api/data/snapshot.db`. Usa `VACUUM INTO` o la API de backup de better-sqlite3; no copies el archivo con la BD abierta.
  - `POST /api/demo/restaurar`: reemplaza el contenido actual con el snapshot de forma segura (sin dejar conexiones de Prisma con datos viejos) y responde el resultado de verificar.
- Si no hay snapshot → 409 con un mensaje claro.
- README del API, sección **"Ataque manual con sqlite3"**:
  - Instalar `sqlite3` (`sudo apt install sqlite3`).
  - Comando de ejemplo: `UPDATE Persona SET nombre='Mallory' WHERE id=1;`.
  - Luego verificar en la UI.

## Criterios de aceptación

- [ ] e2e: snapshot → ataque → restaurar → `valida: true` y la cantidad de bloques es igual a la original.
- [ ] e2e: restaurar sin snapshot → 409.
- [ ] La guía manual está en el README y se probó a mano una vez (anótalo en las notas).
