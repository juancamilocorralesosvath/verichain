# H7.3 — Exportar la cadena para verificación independiente

## Contexto

Diseño §5.9 y §7b "El verificador independiente no confía en el JSON para la llave del servidor".

## Especificación (no cambiar sin actualizar el diseño)

- `GET /api/cadena/exportar` (admin y auditor) → archivo `cadena-AAAAMMDD-HHmm.json`:
  ```json
  {
    "formato": "bc-export/1",
    "exportado_en": "ISO",
    "dificultad": 4,
    "bloques": [ BloqueCadena, ... ],
    "llaves_usuarios": { "<llave_id>": "<spki_b64>" },
    "sello": { "indice": 0, "hash_cadena": "...", "firma": "..." },
    "llave_servidor_spki_b64": "...",
    "huella_llave_servidor": "<sha256 hex del SPKI DER>"
  }
  ```
  `bloques[].persona` lleva la `FilaPersona` con los campos **cifrados**, nunca descifrados.
- En core: `export function parsearExportacion(json: unknown): Exportacion`. Valida la estructura a mano o con una librería ligera e isomórfica. Si el formato es desconocido, lanza error.
- Para el verificador independiente: la llave del servidor que se usa es la **fijada por el usuario** (archivo PEM aparte). La del JSON solo se compara con ella.

## Criterios de aceptación

- [x] e2e: exportar → `parsearExportacion` → `verificarCadena` (con un verificador de Node) → mismo resultado que `GET /verificar`.
- [x] e2e: el JSON exportado no contiene ningún teléfono ni dirección en claro (busca los valores originales del test dentro del texto).
- [x] Prueba de core: un JSON con `formato` desconocido o sin campos → error claro.

## Notas de traspaso

### Decisiones tomadas

- **Formato `bc-export/1`** tal como lo fija la historia (sin cambios al diseño): `formato`, `exportado_en`, `dificultad`, `bloques` (`BloqueCadena[]`), `llaves_usuarios` (`llave_id` → SPKI base64; incluye las llaves **aprobadas y reemplazadas**, para que los bloques viejos sigan verificando), `sello` (el vigente, o `null` si no hay), `llave_servidor_spki_b64` y `huella_llave_servidor`. Las filas de `persona` llevan siempre dirección y teléfono **cifrados**: la exportación nunca descifra.
- **`GET /api/cadena/exportar`** (admin y auditor) responde el JSON con `Content-Disposition: attachment; filename="cadena-AAAAMMDD-HHmm.json"` (UTC). Se lee por la cola de anexos y comparte `leerEstado()` con `verificar`, así los dos ven exactamente los mismos datos.
- **core:** `parsearExportacion(json)` valida la estructura a mano (hashes de 64 hex en minúsculas, base64, enteros, la fila de persona con exactamente los 6 campos, ids de llave enteros positivos) y lanza `Exportación inválida: …` con el motivo; un `formato` desconocido o campos faltantes también. No verifica la cadena: eso es `verificarCadena`.
- **core:** `aOpcionesVerificacion(exportacion, { verificarFirma, llavePublicaServidor })` arma las opciones de verificación y **exige** la llave del servidor fijada por quien verifica; la del JSON solo sirve para compararla (§7b). Con la llave vacía lanza error. Esto es lo que usarán el CLI (H8.1) y la página (H8.2).
- **Pruebas:** core (91 en total) y e2e: exportar → parsear → `verificarCadena` con el verificador de Node da **el mismo reporte** que `GET /verificar`, tanto con la cadena íntegra como con una cadena truncada; el texto del JSON no contiene ninguna dirección ni teléfono en claro; cabeceras, contenido y permisos (admin y auditor sí, registrador 403, sin sesión 401).
